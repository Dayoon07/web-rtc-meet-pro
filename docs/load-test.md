# 부하·강도·급증·오래 버티기·회복·화상회의 테스트 (2026-11-14)

**결론**: 운영 서버 한 대(2 vCPU · 8GB)로
- 채팅은 **동시 접속 800명까지 오류 없이** 버틴다. 1,000명부터 느려지고(느린 5% 가 3초) 실패가 섞이며, 1,500명이면 메시지가 1분 가까이 늦게 와서 못 쓴다.
- **한꺼번에 로그인**은 10초에 150명까지 괜찮고, 10초에 300명이면 실패는 없지만 로그인에 최대 20초 넘게 걸린다.
- 화상회의는 **서버 전체에서 동시에 약 100명**(UDP 포트 201개 ÷ 1인 2개)이 상한이다. 카메라를 켠 사람은 받는 쪽 대역폭 50Mbps 기준 **약 35명**이 먼저 한계다.

## 어떻게 쟀나

| | |
|---|---|
| 서버 | 이 저장소의 서버 jar 를 **CPU 2개(작업 관리자 선호도 고정) · 메모리 1.15GB**(운영 컨테이너 1.5GB × 75%)로 실행 |
| DB | 로컬 Oracle XE 21c (CPU 2개 · 메모리 2GB 제한 = 운영 Oracle Free 와 같은 제한) |
| 사용자 | 테스트 계정 2,000명(10명씩 팀 200개, 팀마다 채널 하나). 웹 클라이언트처럼 행동: 로그인 → 실시간 연결(STOMP) → 처음 화면 5개 요청 → **1인당 평균 1분에 메시지 1개** → 남의 메시지를 받으면 안 읽은 수 · 채팅 목록 · 읽음 처리 3개 요청 (실제 부하의 대부분) |
| 측정 | 요청마다 걸린 시간, 메시지가 보낸 사람 → 다른 사람 화면까지 걸린 시간(도착), 서버·DB CPU·메모리(2초마다) |
| 한계 | 부하를 만드는 프로그램도 같은 PC(Core Ultra 5 125H, 16GB)에서 돌아서 실제보다 조금 불리하다. 메일 발송은 끄고 쟀다 |

표의 "보통" 은 가운데 값(p50), "느린 5%" 는 100번 중 느린 쪽 5번째(p95).

## 1. 부하 테스트 (1분 동안 들어오고 2분 유지)

| 동시 사용자 | 초당 요청 | 오류 | 메시지 보내기 보통 / 느린 5% | 도착 보통 / 느린 5% | 서버 CPU 평균 (최대 200%) |
|---|---|---|---|---|---|
| 100 | 35 | 0 | 0.02초 / 0.13초 | 0.04초 / 0.2초 | 19% |
| 250 | 88 | 0 | 0.02초 / 0.24초 | 0.05초 / 0.5초 | 27% |
| 500 | 167 | 0 | 0.07초 / 1초 | 0.07초 / 1.4초 | 49% |
| 1,000 | 148 | 3.4% | 0.1초 / 22초 | 0.1초 / 28초 | 67% |

1,000명은 **1분 안에 1,000명이 로그인**(초당 17명)해서 무너졌다 → 아래 "발견한 문제 1".

## 2. 강도 테스트 (5분에 걸쳐 천천히 로그인한 뒤 2분 유지)

| 동시 접속 | 초당 요청 | 오류 | 메시지 보내기 보통 / 느린 5% | 도착 보통 / 느린 5% | 서버 CPU 평균 | DB CPU 평균 |
|---|---|---|---|---|---|---|
| **800** | 217 | **0** | 0.07초 / 1초 | 0.09초 / 1.1초 | 54% | 29% |
| 1,000 | 252 | 0.4% | 0.26초 / 2.7초 | 0.35초 / 3.3초 | 67% | 35% |
| 1,500 | 290 | 0.7% | 1초 / 4.8초 | **8초 / 58초** | 78% | 38% |

CPU 는 다 쓰지 않았는데 느려진다 → 막히는 곳은 DB 연결(기본 10개)이다.

|---|---|---|
| 150명 | 0 | 2초 / 7초 |
| 300명 | 0 | 4.7초 / **22초** |

## 4. 오래 버티기 테스트 (600명이 15분 동안)

오류 0, 메시지 보내기 느린 5% 0.6초. 서버 메모리 처음 1/4 평균 1,078MB → 마지막 1/4 평균 1,068MB (늘지 않음 = 메모리가 새지 않는다).

## 5. 회복 테스트 (300명이 쓰는 중에 서버를 강제로 끄고 다시 켜기)

- 강제 종료 → 다시 응답까지 36초 (그중 서버 시작 시간이 대부분). 그동안 요청은 실패한다 (화면은 "보내지 못했어요", 쓴 글은 남는다).
- 서버가 응답하자 **2초 만에 297명 전원이 실시간 연결을 다시 맺었다** (웹은 3초마다 다시 시도).
- **데이터 손실 없음**: 서버가 "저장했다" 고 답한 메시지 2,228개가 DB 에 모두 있다 (DB 2,288개 — 60개는 저장은 됐는데 답을 받기 전에 서버가 꺼진 것. 사용자가 다시 보내면 두 번 올라갈 수 있다).
- 다시 켠 직후 297명이 한꺼번에 채팅 목록을 다시 불러와 몇 초 동안 처리 시간 초과가 났다 → "발견한 문제 3".

## 6. 화상회의

크롬(헤드리스, 가짜 카메라·마이크)을 여러 개 띄워 한 회의에 넣었다.

| 회의 인원 | 들어온 사람 | 미디어 서버 CPU 평균 (코어 1개 = 100%) | 이 PC CPU |
|---|---|---|---|
| 4 | 4 (카메라 4) | 10% | 41% |
| 8 | 8 | 15% | 47% |
| 12 | 9 | 31% | 67% |
| 16 | 12 | 25% | 69% (최대 89%) |

- 12명부터 다 못 들어온 것은 **테스트하는 PC 쪽 한계**(크롬 하나가 영상을 만들고 남의 영상을 다 받는다)다. 미디어 서버는 12명 회의에 CPU 1개의 약 30% 를 썼다 (워커 2개).
- 무료 플랜 팀은 회의가 **6명에서 막힌다** (플랜 한도가 제대로 걸린다).
- **포트 한도 확인**: 미디어 서버 포트를 10개로 줄이고 6명 회의를 열자 5명만 연결되고 "no more available ports" 가 났다. 참가자 1명 = 연결 2개(보내기·받기) = UDP 포트 2개. 운영은 포트 40000~40200(201개) → **서버 전체 동시 약 100명**.
- 대역폭: 카메라 1명이 최대 약 1.3Mbps 를 올린다(화질 3단계 동시 전송). 받는 쪽 50Mbps(iwinv 별도 계약 기준) → 카메라를 켠 사람 약 35명. 트래픽은 4명 1시간에 약 6~7GB.

## 발견한 문제와 고칠 거리

| # | 문제 | 영향 | 고치는 법 |
|---|---|---|---|
| 1 | 로그인할 때 비밀번호 확인(bcrypt, CPU 를 많이 씀)을 **DB 연결을 잡은 채로** 한다 | 로그인이 몰리면 DB 연결 10개가 다 묶여 **로그인 안 한 사람의 요청까지** 30초 기다리다 실패 (1,000명 테스트) | 비밀번호 확인을 DB 트랜잭션 밖으로 빼기 + DB 연결 수 10 → 20 검토 |
| 2 | 미디어 포트 201개를 참가자마다 2개씩 쓴다 | 서버 전체 동시 회의 약 100명 | mediasoup `WebRtcServer`(모든 참가자가 포트 하나를 같이 씀)로 바꾸기, 또는 포트 범위·방화벽 넓히기 |
| 3 | 서버가 다시 켜지면 전원이 똑같이 3초 뒤에 다시 연결하고 목록을 다시 부른다 | 재시작 직후 몇 초 동안 시간 초과 | 다시 연결 대기 시간에 무작위(예: 1~5초) 더하기 |
| 4 | 처리 시간 초과(transaction timeout)를 오류 기록이 **"DB 구조 불일치"(DB_SCHEMA)** 로 잘못 분류 | 관리자가 오해 | 오류 분류기에서 "Transaction timed out" 은 DB 연결·시간 초과로 |
| 5 | 답을 못 받은 메시지를 다시 보내면 두 번 저장된다 | 서버 장애 순간에만, 드묾 | (선택) 메시지에 화면이 만든 id 를 붙여 같은 id 는 한 번만 저장 |
| - | 채팅 목록(`/api/teams/{id}/chat/rooms`) 이 가장 무겁고 가장 자주 불린다 | 사용자가 늘면 먼저 느려짐 | 문제 1·3 을 고친 뒤 다시 재 보고 필요하면 가볍게 |

## 다시 돌리기

`scripts/load-test/` (Node 22 · Python psutil, 설치할 것 없음)

```bash
# 1) 테스트 서버: CPU 2개 · 메모리 1.15GB · 메일 끄기 (포트 8082)
cd apps/server && ./gradlew bootJar
SERVER_PORT=8082 MAIL_HOST= STORAGE_TYPE=local java -Xmx1152m -XX:ActiveProcessorCount=2 -jar build/libs/server-0.0.1-SNAPSHOT.jar
#    (PowerShell 로 그 java 프로세스의 ProcessorAffinity 를 5 = CPU 2개로)
# 2) 테스트 계정·팀
node scripts/load-test/setup.mjs signup 2000
sqlplus -S limeet/limeet@//localhost:1521/XEPDB1 @scripts/load-test/verify.sql
node scripts/load-test/setup.mjs teams
# 3) 단계별: 접두어, 사용자 수들, 유지 초, 들어오는 초, 메시지 간격 초
./scripts/load-test/stages.sh load "100 250 500 1000" 120 60 60
./scripts/load-test/stages.sh stress "800 1000 1500" 120 300 60
./scripts/load-test/stages.sh spike "150 300" 60 10 60
./scripts/load-test/recovery.sh
node scripts/load-test/meeting.mjs --people 8 --seconds 60   # 미디어 서버·웹(5175)을 8082 에 붙여서
# 4) 지우기 (ID 범위를 확인하고 바꿔서)
sqlplus -S limeet/limeet@//localhost:1521/XEPDB1 @scripts/load-test/cleanup.sql
```

결과(JSON)는 `scripts/load-test/results/` 에 쌓인다 (테스트 계정 토큰이 있어서 git 에 올리지 않는다).
